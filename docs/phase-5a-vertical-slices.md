# Phase 5a — Vertical slices (4 PRs)

> **Status:** slicing plan for the Phase-5a scope (`docs/phase-5a-offline-mobile-scope.md`).
> **Branch:** `ofp-monorepo`.
> **Goal:** every PR lands, tests, ships, and is revertable without breaking the rest.

## 1. Why slice vertically

The scope doc estimated ~30 files across server, schema, and mobile. That's a single merge risk: any of the four hard parts (schema version column, LWW conflict detection, durable outbox, signed-upload pipeline) breaks the whole PR. Slice into 4 PRs so:

1. **Each PR has its own story.** "Sync route exists", "Mobile reads offline", "Mobile writes offline", "Photos work offline".
2. **Each PR is revertable.** If PR 3 (outbox) hits a flaky non-determinism, you revert one PR instead of 30 files of diff.
3. **Each PR can stand behind a feature flag** if needed (e.g. `OFP_OFFLINE_OUTBOX`).
4. **Each PR ships its own test suite** — server-side tests in PRs 1+4, mobile-side tests in PRs 2+3.

## 2. Sequencing at a glance

```
PR 1 ──┬──> PR 2 ──┬──> PR 3
       │          │
       └──> PR 4 ──┘
```

- **PR 1** (schema + sync route + executor) is the foundation. PRs 2, 3, 4 all depend on it.
- **PR 2** (mobile mirror + delta) reads from PR 1's sync endpoint.
- **PR 3** (outbox + drain) writes to PR 1's sync endpoint.
- **PR 4** (photos + signGet) is orthogonal — adds a new endpoint + a new mobile flow; can land in parallel with PR 2 or PR 3 once PR 1 is in.
- PR 2 and PR 3 must land in order (outbox needs mirror).
- **PRs 1 and 4 are independent of each other** once the schema bump is on `main`.

## 3. PR 1 — schema + sync route + executor (server)

**Story:** Tech can `POST /api/sync` and the server reconciles operations with last-write-wins conflict detection.

**Files (new):**

- `packages/db/src/schema.ts` — add `version integer default 1 not null` and `updated_at timestamp` to 7 tables: `jobs`, `line_items`, `invoices`, `appointments`, `customers`, `estimates`, `payments`. Drop `defaultRandom()` on `id` for the 4 hot-path tables (`jobs`, `line_items`, `invoices`, `appointments`) so the API requires an `id` field; the other 3 keep `defaultRandom()` (clients never write them offline).
- `packages/db/drizzle/0001_add_version_cols.sql` — auto-generated by `pnpm --filter @ofp/db generate` for the column additions, plus a raw-SQL block for the `BEFORE UPDATE` trigger (`NEW.version = OLD.version + 1`).
- `apps/api/src/sync/executor.ts` — pure op-router; accepts `{op: 'create'|'update'|'delete', table, id, payload, version}`; runs each op in a transaction; bumps version; returns canonical row on conflict.
- `apps/api/src/routes/sync.ts` — `POST /api/sync` accepting `{ops: SyncOpDTO[]}`; runs each op through the executor; returns `{results: SyncResultDTO[]}`.
- `packages/shared/src/index.ts` — add `SyncOpDTO`, `SyncResultDTO`, `SyncRequestDTO`, `SyncResponseDTO`.
- `apps/api/src/server.ts` — register `syncRoutes` at `/api/sync`; add `@fastify/multipart` plugin (needed by PR 4 but registered here so we don't re-touch `server.ts` later).

**Files (mod):**

- `apps/api/src/server.ts` (+5).

**Tests (in-process, no DB required for executor unit tests):**

- `executor.test.ts`:
  - `update` op with matching version → returns `{status: 'accepted', row}`.
  - `update` op with stale version (`payload.version < stored.version`) → returns `{status: 'conflict', row: <canonical>}`.
  - `create` op → assigns orgId from JWT; rejects if request body omits `id`.
  - `delete` op with stale version → returns `conflict`.
- `routes/sync.test.ts`:
  - Empty ops array → returns `{results: []}`.
  - Mixed ops in one request → all run; partial failures don't abort the request.
  - Auth required: no JWT → 401.

**Smoke test (after merge):**
```bash
# start api with dev DB, then:
curl -X POST http://localhost:3001/api/sync \
  -H "Authorization: Bearer $JWT" \
  -H "Content-Type: application/json" \
  -d '{"ops":[{"op":"create","table":"jobs","id":"<uuid>","payload":{"customerId":"...","title":"test"},"version":1}]}'
# Expect 200 with result.status === "accepted"
```

**Size est.:** ~10 new files, ~330 LoC. Migration adds 2 columns × 7 tables + 1 trigger (~50 lines of SQL).

**Risks:**
- Dropping `defaultRandom()` is a one-way API contract change. **Mitigation:** only on 4 hot-path tables; the route rejects `create` ops without `id`; old clients keep using existing POST endpoints.
- `BEFORE UPDATE` trigger must be raw SQL — `drizzle-kit generate` won't write it. **Mitigation:** add the trigger block as a second SQL block in the migration file.

## 4. PR 2 — mobile mirror + delta

**Story:** Tech opens the mobile app and sees their assigned jobs even when offline. New jobs/lines sync down when online.

**Depends on:** PR 1.

**Files (new):**

- `apps/mobile/app/_layout.tsx` — root layout with auth gate.
- `apps/mobile/app/(tabs)/jobs.tsx` — list of assigned jobs, offline-aware `queued` / `syncing` / `sent` badge per row.
- `apps/mobile/app/(tabs)/job/[id].tsx` — read-only screen showing job + line items.
- `apps/mobile/src/api/client.ts` — fetch wrapper with JWT injection, exponential backoff, 401 → re-auth, 409 → resync.
- `apps/mobile/src/sync/store.ts` — `expo-sqlite` local mirror of `jobs`, `line_items`, `customers`, with a `meta` table tracking `synced_at` per org.
- `apps/mobile/src/sync/delta.ts` — `GET /api/sync?since=<timestamp>` for per-org deltas; merge into local store.
- `apps/mobile/src/auth/login.tsx` — login screen + `expo-secure-store` JWT storage.
- `apps/mobile/App.tsx` — wire `NavigationContainer` + `Stack.Navigator` for Login → tabs.

**Files (mod):**

- `apps/mobile/package.json` — add `expo-sqlite`, `expo-secure-store`, `@react-navigation/native`, `@react-navigation/native-stack`.
- `apps/app.json` — add `expo-secure-store` to plugin list (RN requirement on iOS).

**Tests:**

- `store.test.ts`:
  - Insert, update, delete a job; survives restart (sqlite committed).
  - Delta merge: incoming newer wins; incoming older is discarded.
- `client.test.ts`:
  - 401 → triggers re-auth flow.
  - 409 → triggers resync delta.
- `delta.test.ts`:
  - `since` filter respected; new rows only since timestamp returned.

**Smoke test:**
```bash
# Login with valid tech creds.
# App shows assigned jobs.
# Airplane mode → reopen → jobs still visible.
# Online → pull-to-refresh → newly-assigned jobs appear.
```

**Size est.:** ~8 new files, ~520 LoC. No server changes.

**Risks:**
- `expo-sqlite` write contention under high offline churn. **Mitigation:** use single-writer DB promise queue; wrap each migration step in a transaction.
- JWT expiry mid-session. **Mitigation:** 30-day JWT (per scope doc §3.5); one in-app retry on 401.

## 5. PR 3 — outbox + drain

**Story:** Tech creates a job and adds 3 line items in airplane mode. Reconnects → all 4 operations sync to server in order.

**Depends on:** PR 1, PR 2.

**Files (new):**

- `apps/mobile/src/sync/outbox.ts` — `expo-sqlite` `outbox` table (`id`, `op`, `table`, `row_id`, `payload_json`, `version`, `attempts`, `created_at`, `last_error`); `enqueue/peek/mark_done/mark_failed` helpers.
- `apps/mobile/src/sync/drain.ts` — `AppState` listener: on `background → active`, drains outbox in FIFO order with exponential backoff (1s / 5s / 30s / 5m).
- `apps/mobile/app/(tabs)/job/[id].tsx` (mod) — wire "Add line item" button to enqueue + apply optimistically to mirror.

**Files (mod):**

- `apps/mobile/app/(tabs)/job/[id].tsx` (mod) — `enqueue('update', 'line_items', ...)` on submit.

**Tests:**

- `outbox.test.ts`:
  - Enqueue, peek returns FIFO order.
  - `mark_done` removes; `mark_failed` records `last_error` + increments `attempts`.
- `drain.test.ts` (with mocked `AppState` and `fetch`):
  - AppState `active` → drain called.
  - Drain retries on transient 5xx up to `attempts` cap; abandons on `attempts = 5` + surfaces a "Retry" button.
  - Drain respects FIFO order across 3 enqueued ops.

**Smoke test:**
```bash
# Airplane mode.
# Tech adds job, adds 3 line items, takes 1 photo (placeholder if PR 4 not yet merged).
# Online → reopen app → outbox drains → ops appear in OFP web dashboard in order.
```

**Size est.:** ~3 new files, ~150 LoC. Pure mobile-side.

**Risks:**
- Outbox durability = local SQLite only (per scope §4.1). **Mitigation:** `ponytail:` comment in `outbox.ts` naming the upgrade path (server-side `pending_ops` mirror).
- Conflict loss (LWW). **Mitigation:** per scope §4.2, server returns canonical row on conflict; mobile surfaces "Edited remotely, server's version kept" banner.

## 6. PR 4 — photos + signGet

**Story:** Tech takes a job photo offline; the photo uploads to MinIO the moment the device reconnects, with no bytes through the Fastify server.

**Depends on:** PR 1 (`@fastify/multipart` is registered in PR 1).

**Files (new):**

- `apps/api/src/uploads/minio.ts` — MinIO SDK wrapper; reads `MINIO_ENDPOINT` / `MINIO_ACCESS_KEY` / `MINIO_SECRET_KEY` / `MINIO_BUCKET` from env.
- `apps/api/src/routes/uploads.ts` — `POST /api/uploads/presign` returning `{url, key, expires_in}` for PUT (TTL = 15 min); `POST /api/uploads/signGet` returning `{url}` for GET (TTL = 1 hour).
- `apps/mobile/app/(tabs)/job/[id].tsx` (mod) — photo button → `expo-image-picker` → `expo-file-system.uploadAsync` to pre-signed PUT.
- `apps/mobile/src/photos/picker.ts` — helpers: `pickImage()`, `compressForUpload()` (resize to max 1600px), `uploadViaPresigned()`.
- `apps/mobile/src/photos/queue.ts` — photo upload queue (parallel-ish by hand; simpler than outbox for binary content).

**Files (mod):**

- `apps/mobile/package.json` — add `expo-image-picker`, `expo-file-system`, `expo-camera` (optional).
- `apps/mobile/app.json` — `expo-image-picker` needs usage descriptions on iOS.
- `apps/api/.env.example` — add `MINIO_*` vars.
- `packages/shared/src/index.ts` — add `PresignRequestDTO`, `PresignResponseDTO`.

**Tests:**

- `minio.test.ts`:
  - `presignPut('jobs/abc/photo.jpg')` returns URL with TTL ~15 min.
  - `signGet('jobs/abc/photo.jpg')` returns URL with TTL ~1 hour.
- `routes/uploads.test.ts`:
  - `POST /api/uploads/presign` without JWT → 401.
  - With JWT → returns `{url, key, expires_in: 900}`.
- `mobile/picker.test.ts`:
  - Compression resizes a 4032×3024 image to ≤1600px (pixel-count check).
  - `uploadViaPresigned` lifecycle: PUT URL → 200 → rows cached locally with key.

**Smoke test:**
```bash
# Tech takes a job photo online → pre-signed PUT issued → bytes go directly to MinIO → DB stores key.
# Same flow offline → photo stored locally with key + queued → drains after reconnect.
# Sign GET → any client can render with a fresh 1-hour URL.
```

**Size est.:** ~5 new files, ~280 LoC. Server + mobile, both new files.

**Risks:**
- MinIO credentials absent → pre-sign fails → photo can't upload. **Mitigation:** server returns clear 503 to mobile; mobile shows "Photo queued — waiting for server"; `ponytail:` comment in `minio.ts` naming the upgrade path (server-side virus-scan + thumbnail pipeline).
- 15-min PUT TTL means mobile MUST start the upload within 15 min of getting the URL. **Mitigation:** pre-sign at the moment of upload, not at the moment of capture.
